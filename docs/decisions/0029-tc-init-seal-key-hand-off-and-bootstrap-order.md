# tc init writes the seal key OpenBao waits for, then finishes the bootstrap through the Backend Plugin

## Context and Problem Statement

ADR-0008 has `tc init` initialize the bundled OpenBao with the static seal and show the Operator the unseal key and recovery material once, with TrustedCourier keeping none of it. OpenBao needs the static seal key before it starts, and `sys/init` can only run once it has. In a compose stack, where does the key live, who writes it, and in what order do the containers come up? Beyond OpenBao, a working deployment also needs the Backend Plugin's token, the audit signing key (ADR-0019), and the Operator Credential; who creates those, and through which path?

## Considered Options

* The OpenBao container generates the seal key on first start; `tc init` shows it by reading the file
* `tc init` generates the key into a volume OpenBao mounts; OpenBao's start command waits for it, then hands it over
* `tc init` shells out to `docker compose` to order the start
* Store the audit signing key with OpenBao's API from `tc init`
* Store the audit signing key through the Plugin Host and the Backend Plugin
* Revoke the initial root token after setup; keep and show it
* Create the Operator Credential in `tc init`; leave it to the server's first boot

## Decision Outcome

Chosen options: "`tc init` generates the key, OpenBao waits for it", "through the Plugin Host", "keep and show the root token", and "create the Operator Credential in `tc init`".

* The seal key is OpenBao's material. `tc init --seal-key-file <path>` writes 32 random bytes there, owner-only, when the file is absent, and shows them in base64 once. The path is never under TrustedCourier's data directory; in the compose file it is a volume both containers mount, TrustedCourier's side read-write, OpenBao's read-only. OpenBao's container start command waits for the file, puts its base64 in `BAO_SEAL_KEY`, and starts OpenBao through its own entrypoint, so OpenBao runs as its own user and the file stays root-only. `tc init` polls OpenBao until it answers, so `docker compose run trustedcourier tc init` and `docker compose up -d` work in either order. Having OpenBao generate the key was rejected because ADR-0008 makes `tc init` the generator and the bare-binary path, with no compose, needs one anyway. Shelling out to compose was rejected because `tc` would then depend on docker, and could not run inside the container it ships in.
* `tc init` refuses to touch anything until the config loads and the Plugin Host accepts every plugin (pinned SHA-256, separate user), and refuses an OpenBao that is already initialized, unless a root token in `BAO_TOKEN` says the Operator wants it to finish a bootstrap that stopped part way. `--dev` skips the seal and takes the root token from `BAO_DEV_ROOT_TOKEN_ID`, the variable OpenBao's dev server takes, so a compose file sets it once.
* Recovery keys and the root token are printed the moment `sys/init` returns, before any step that can still fail: a later failure must not lose the only copy. Recovery shares default to OpenBao's 5 of 3 and are flags.
* The Backend Plugin's token is an orphan with the `trustedcourier` policy, written to `BAO_TOKEN_FILE` from the plugin's `env`, mode 600, and given to the plugin's user. The lifetime is a flag defaulting to a year, which the compose file's OpenBao allows by `max_lease_ttl`; OpenBao caps it otherwise and `tc init` prints the expiry it got, since the plugin does not renew (ADR-0028).
* The audit signing key is generated by `tc init` and stored by running the Backend Plugin once, through the Plugin Host, exactly as the server will: hash verified, user switched, `WriteCourierKey`, then read back. Writing OpenBao's KV API directly was rejected because the core would then know OpenBao's location syntax, and the run doubles as proof the plugin works before the server starts. An existing key is kept, so a rerun never breaks the audit chain.
* The initial root token is kept and shown: the Operator needs a token to store Secrets, and the procedure to make another from recovery keys is OpenBao's, not ours. The docs tell the Operator to keep it offline; it is not on any TrustedCourier disk.
* `tc init` creates the Operator Credential through the same `EnsureOperatorCredential` the server uses, so the whole bootstrap shows its material in one sitting and the server's first boot shows nothing. A server that boots first still creates it, and `tc init` then says so.

### Consequences

* Good, because one compose file and one command give a running broker, and every secret the bootstrap made is shown once, in one place.
* Good, because `tc init` exercises the pinned plugin end to end before the server ever runs.
* Bad, because the seal key sits on a volume on the same host as OpenBao's data, which is a convenience, not a security boundary (ADR-0008); the docs say so and point at KMS and HSM seals.
* Bad, because the OpenBao container's start command is a shell one-liner the tests must keep in step with (the harness checks the compose file matches).
* Bad, because a `tc init` interrupted after `sys/init` needs the Operator to rerun it with `BAO_TOKEN`.
