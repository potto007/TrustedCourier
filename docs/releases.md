# Release automation

The Release workflow builds `tc` and the bundled OpenBao Backend Plugin for
Linux and macOS, each on amd64 and arm64. Windows is not a supported server
platform. Linux archives additionally include the experimental `tc-exec` and
`tc-claude-hook` helpers, public Claude plugin/marketplace, and integration guides.
These integrations require Linux/WSL and are not shipped as macOS helpers.
The packaged Claude plugin version matches the release tag. Each target builds and smoke-tests on a matching GitHub runner.

## Validate without publishing

Pull requests that change release tooling or dependencies build preview archives.
After the workflow is on `main`, **Actions > Release > Run workflow** also builds
preview artifacts for the selected branch. A manual run never publishes, even
if invoked against a tag. Download the four `release-*` workflow artifacts.
`v0.0.0-preview` is an artifact label, not a release tag or supported version.
The ordinary CI workflow runs the full test suite for pull requests.

For a native local build, with Go from `go.mod` and Python 3 on PATH:

```sh
sh scripts/build-release.sh build/release
python3 scripts/package-release.py v0.0.0-preview linux_amd64 build/release dist
```

Use the matching platform name when building elsewhere. Packaging verifies the
binary checksums, zero-CGO setting, versioned FIPS module, and target platform.
The archive contains its platform binaries, their `SHA256SUMS`, `LICENSE`,
`README.md`, and `BUILD-INFO.json` (commit and Go dependency/build metadata).
No configuration, credentials, or deployment state is included.

## Publish a reviewed version

1. Merge the reviewed changes after CI and DCO pass. Choose the version explicitly.
2. Create and push an annotated tag on the intended commit on `main`, using
   `vMAJOR.MINOR.PATCH` or a prerelease such as `v1.0.0-rc.1`. Do not move release tags.
3. The tag-triggered Release workflow verifies tag syntax and that the commit is
   in `main` history, runs the full six-leg module/FIPS race-test matrix and root
   isolation checks, and builds and smoke-tests all four packages.
4. Only after every gate passes does a job with `contents: write` create a draft,
   upload the four archives and their aggregate `SHA256SUMS`, then publish it.
   A tag with a prerelease suffix is marked as a GitHub prerelease.

No version is automatically chosen, no tag is automatically created, and manual
validation cannot publish. Checkout/build jobs only have read permission.
The workflow uses the repository's `GITHUB_TOKEN`; no personal token is required.
Release notes are generated by GitHub and can be edited by the maintainer.
When present, `docs/release-notes/<tag>.md` is prepended before publication.

If a build/test fails, fix it and choose a new tag when source changes are needed.
If only uploading or publication fails, inspect the remaining draft and assets.
The workflow refuses to overwrite an existing release. Delete an incomplete draft
before rerunning the failed publish job; do not replace published assets.

## Verify a download

Download the platform archive and the release-level `SHA256SUMS` together.
Verify the archive hash with `sha256sum --check --ignore-missing SHA256SUMS` on
Linux, or compare `shasum -a 256 <archive>` against the matching manifest entry
on macOS. After extracting, run `shasum -a 256 -c SHA256SUMS` inside the package.
The inner manifest hashes the binaries and provides the OpenBao plugin hash for
configuration pinning. Checksums detect corruption; they are not signatures.

The core and OpenBao binaries link Go's validated FIPS module (`GOFIPS140=certified`) and default
to FIPS mode off under ADR-0027. Set `GODEBUG=fips140=on` when required. Linking
that module does not constitute certification of TrustedCourier itself. macOS
artifacts are unsigned and not notarized; follow your organization's execution
policy. No container image or independent SDK release is published by this workflow.
